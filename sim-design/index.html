The Persona Switcher

Sim mode moves out of a tab and onto the top bar. One chip — top-left, mirroring the Code chip top-right — swaps your entire screen between Operator and any simulated player, running the real player UI on an isolated sim namespace. No mocks, no screenshots, no parallel implementation.

Why this works

The whole app already routes through one seam

GamePage picks a screen by identity: operator → OperatorGamePage, player → PlayerGamePage. Both take the same two props — gameId and currentUserId. And every record read/write in the app flows through hooks/useData.ts.

PlayerGamePage · TownSquare · EyesOnly
rule 1 — game-scoped reads: itemId === gameId → "{gameId}:sim" (all lists except 'games') rule 2 — user-scoped records: key for a persona record → "sim:{persona}:{key}" (operator-owned, writable)

Rule 2 is the upgrade over the old plan: instead of a one-off submissions seam, every per-user record gets a per-persona clone — userData, playerProfile, and the findValues submission records. The faux player's submit button writes a real record through the real mutation path. The previous "one injection point" becomes zero.

What this buys: the actual PlayerGamePage mounts — real tab bar, real Town Square, real Your Eyes Only, real submit → plan → certify loop — and it cannot touch the live game because every key it resolves is namespaced. The operator's own records are the only ones ever written; personas are just key suffixes.

Mechanics

How a persona resolves, step by step

On "View as Faux Willow"
  1. Seed once — sim userTable gets a Willow row (email willow@sim.local); persona records sim:willow:userData and sim:willow:playerProfile:{simId} are written with her name so the claim gate passes.
  2. Mount — GamePage renders PlayerGamePage with currentUserId="sim:willow" + a SimProvider.
  3. Redirect — useData rewrites keys: lists → :sim, persona records → sim:willow:….
  4. Gate passes — matchingPlayer finds Willow in the sim userTable by her seeded email; profile loads pre-claimed. Player tabs render.
What each persona sees
  • Town Square — posts under :sim. Every persona (and the sim console) posts into the same sim square.
  • Your Eyes Only — her role message, her cells, her submission inputs. Submit writes her real record.
  • Newspaper — sim issues; certify from the console publishes into the sim only.
  • Phone Book — sim profiles of the other faux players.
  • Day dial — writes selectedDayIndex:{simId}; every persona + console shares the same sim "now".
useValue("userData") → "sim:willow:userData" useSharedListValue("userTable") → itemId "{gameId}:sim" useFindValues(submissionKey) → "sim:willow:{key}" setValue("playerProfile:…") → writes "sim:willow:…"
The 'games' list is the one exemption: there is no sim game row, so useFindListItems('games') keeps the real gameId. That's correct on purpose — useGameOperatorUserId still resolves the real operator (who owns all sim records), while the persona switcher — not the ownership check — decides which screen mounts.

Workflow

A testing session, top to bottom

  1. Open the switcher — top-left chip. "Manage faux players" seeds the sim cast (or "Import real cast" copies tonight's live userTable).
  2. View as Faux Willow — the whole screen is her game: real player tabs, real Town Square. Her Eyes Only shows the werewolf script she'd see.
  3. Play her turn — type a real submission; it lands in sim:willow:…. Switch persona, repeat. Two clicks per player, no console needed for happy-path staging.
  4. Console → Certify — swap to the sim operator view, hit Review/Certify. Real PlannedUpdates, provenance ops, tag triggers, morning writes — all in the sim namespace.
  5. Turn the dial — ◀ ▶ through days; every persona shares the sim clock. View as Alder to check his morning message landed.
  6. Poke it — recertify, remove a tag, starve a submission, view as a dead player. The live game never notices.
  7. End simulation — chip → "End simulation" (or just pick "Operator"). Sim records stay namespaced; "Reset" wipes them.
State & reload: the session (active persona + sim day) persists in a per-user record simSession:{gameId}, so a reload lands you back where you were. Tabs inside the persona view are ordinary React state, same as today — no router changes, no back-button weirdness.
Plan

What it costs to build — and what could bite

Phase 1 — the switcher
  • SimContext + the two redirect rules in useData.ts
  • Persona chip + menu in MainPage (top-left)
  • PlayerGamePage mount with simIdentity gate prop
  • Persona seeding (userTable row + userData + profile)
  • Sim strip (switch / console / back-to-operator)
Phase 2 — the console persona
  • OperatorGamePage on :sim + console strip
  • Snapshot-copy config records (roles, files, tag defs, schedule)
  • Faux roster CRUD, "Import real cast", Reset / Re-sync
  • Day dial → selectedDayIndex:{simId}
Phase 3 — depth
  • Ghost persona (dead-player UI paths)
  • Scripted scenarios via the esbuild+node smoke harness
  • Perf: ensure redirect adds no render overhead when sim is off
Edge cases to get right
  • 'games' list exemption — sim id has no games row; ownership lookups must keep the real id (one allowlist entry in the redirect).
  • Profile-claim gate — seeded profiles skip it; an un-seeded persona would show the claim dialog (that's a valid test too).
  • Non-persona user records — activeGameId, customUserInfo stay real (they're about you, not the persona); the redirect only rewrites keys that carry the game scope or persona opt-in list.
  • Write path — setValue must redirect the same way as reads, or persona writes leak to real keys.
  • Minimize/dialog state — persona swap unmounts the tree; minimized cards are scope-keyed, so nothing cross-contaminates.
Perf note (ties into the bigger effort): the redirect is one context read inside useData hooks — zero cost when sim is inactive. Entering a persona remounts the screen once, the same cost as switching games. Nothing hot-path changes.
Open questions: (1) Chip visible to operators only — confirm that's the right gate (it's keyed off the same ownedGameRows check GamePage already makes). (2) Persist sim session across reloads, or always start at Operator? (3) Should "Import real cast" also copy cell state/tags, or roster only?
